## Defect
TWO defects; the schema has one set of singular fields, so T7-A is carried in them and T7-B is stated in full alongside. T7-A (client-side world-prop duplication and frame-rate collapse): reporters say a non-host peer sees two of things the host sees once ("every single item on the map being duplicated for non-host players", "most physics objects are being duplicated on clients", basement crates duped right after a join, 2-9 fps or 2.5 fps only when not hosting). In source terms: the joining client builds its world by loading the host's transferred save, then the host's snapshot reconciles each PropSpawn by exact Key, then a pile-only 30 cm position bind, then a same-class 30 cm fuzzy match, and anything that misses all three materialises a FRESH MIRROR beside the client's own local copy (remote_prop_spawn.cpp fall-through to prop_fresh_spawn::Materialize). The only thing that would delete the now-redundant local copy is join_membership_sweep, and that sweep deliberately KEEPS unclaimed locals in two cases it logs by name -- the per-class completeness floor ("the host under-expressed these classes; the unclaimed locals SURVIVE") and the global >50% valve ("A few stale ghosts beat an empty world"). So local+mirror coexistence is the designed outcome whenever a large fraction of the host's props fail identity reconciliation, and it is client-only by construction because the host never receives the mirrors. The supply of identity misses is measured: the host's own KEY-UNIQUENESS authority (prop_element_tracker.cpp) finds 81 save-born clone-key duplicates on EVERY census re-seed and mints a fresh random rk_<64 bit> key for each; the same physical trashBitsPile_C at loc=(-2190.0,2375.0,6343.3) is re-keyed to four different keys across the reporter's four host world reloads, because the re-key writes only the live actor and the host's on-disk save (which the coop save-block never refreshes) still holds the duplicate. The prop_element_tracker comment states the consequence of that duplicate-key world itself: "the join reconcile then re-expresses them INTO already-occupied positions (take-3: ~75 interpenetrating awake pairs = the 2.5 fps physics storm + scattered props)" -- numerically the same 2.5 fps Nicoszoki reports, in the same episode as duped crates and a peer "noclipping them and moving them effortlessly". T7-B (a rejoining peer gets the host's inventory, and the copies vanish on drop): the joining client's world IS the host's save, including the host's player state. The only substitution the mod performs is player_inventory_sync::OnSaveObjectReady -> ue_wrap::inventory::ApplyToSaveObject, which rewrites ONLY the save-side arrays inventoryData/equipment/hold. The wrapper header states, as a measurement, that inventoryData is a projection written by mainGamemode::saveObjects with NO gameplay reader in the cooked game, and that what a player actually carries lives in mainGamemode.playerContainer.propInventory -> saveSlot.GObjStack[0], for which the same header declares itself "READ-ONLY BY CONSTRUCTION -- there is no live-store writer in this header, on purpose". The carried inventory a client walks into the world with is therefore the host's, and no code path in the mod replaces it. Separately, on any apply miss (blob absent after the 20 s wait, deserialize failure, ApplyToSaveObject failure) the hook deliberately SKIPS and leaves the host's loaded equipment/hold too -- the success log calls itself "RETIRES the v56 host-save inheritance", so the un-applied path IS host-save inheritance. The vanish-on-drop half is the same code's own acknowledged hazard: BuildFirstJoinStarterKit copies the host's live SaveRecords verbatim including their `key` field, and the comment concedes "the copied records carry the host's item KEYS ... only a simultaneous DROP of the same starter item by multiple peers would collide on the world-prop key. Follow-up (regenerate keys) only if that's observed." Two peers holding records with the same key means a drop by either creates a world prop under a key the other peer's index already owns -- the destroy-by-key collision class already recorded as OBS-R3Q-C01 and Report 3 -- which is exactly Aiker228's "those items may disappear after dropping them (even when host drops them)" and Clark item 2's bricked host inventory from a duped shovel.

## Proposed fix
T7-A, ONE BOUNDED FIX that is READY. File src/votv-coop/src/coop/props/prop_synth_key.cpp, function MintFreshKeyForDuplicate (ba6d8c39:102-155, 3af5ddae:102-155, byte-identical). Condition: the fresh key is currently drawn from a process-local std::mt19937_64 seeded from random_device + steady_clock (lines 118-131), so the SAME physical prop in the SAME world gets a DIFFERENT cross-peer identity on every census pass -- measured four times over, four different rk_ keys for loc=(-2190.0,2375.0,6343.3). Replace the random draw with a deterministic derivation over inputs that are stable for that actor in that world: FNV/SHA of (the colliding incumbent Key string || the actor's class leaf name || its spawn transform quantised to 1 mm), keeping the existing rk_%016llx shape and the existing FindLiveActorByKey incumbent check ahead of it. Why it cannot regress the legitimate path: uniqueness is still enforced by the incumbent check that gates entry to this function at prop_element_tracker.cpp:387/253, and two genuine clones of one save key differ in transform so they still receive different keys; a single clone re-visited by a later pass now receives the key it already has, so the pass converges to zero collisions instead of re-shuffling 81 identities per host reload; and nothing outside this function reads the value's randomness (the key is an opaque FName). Second, non-behavioural half of the same change: the re-key currently reaches only the LIVE actor, and the reporter's host reloaded three times and re-collided identically each time, which proves the comment's premise "the new key persists via the game's own save" is false in a coop session (the coop save-block means the host never re-saves). Either the comment must be corrected or the enroll must not depend on persistence -- the deterministic mint makes the persistence question moot, which is why it is the right bounded change. T7-B is split. READY half: in BuildFirstJoinStarterKit (ba6d8c39 player_inventory_sync.cpp:470-491, 3af5ddae:455-476), regenerate SaveRecord::key on every record copied out of the host's own live inventory into another peer's kit (inventory[], equipment[].data, hold[].data), using the same fresh-key mint. It cannot regress the legitimate path because the record's key is only consulted when the item becomes a world actor, and the code's own comment already isolates the collision to exactly that moment. NEEDS_DESIGN half (do not attempt as a patch): the carried inventory a joining client walks in with is GObjStack[0] restored from the host's save, and ue_wrap/actors/inventory.h declares itself read-only for that store on purpose ("there is no live-store writer in this header, on purpose ... gated on the open per-player scope questions"). Making the per-player apply cover what the player actually carries requires either a live-store writer or a pre-materialize edit of the host save's GObjStack[0] slot, and both are the open scope question, not a bounded fix. The interim, bounded mitigation that IS available: OnSaveObjectReady's miss branch (ba6d8c39:319-335, 3af5ddae:306-322) should be loud and should refuse to enter the world rather than silently inheriting -- but that changes a deliberately fail-safe "never wipe" decision, so it is a design item too.
