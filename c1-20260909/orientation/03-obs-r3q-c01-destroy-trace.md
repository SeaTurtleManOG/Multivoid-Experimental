# SUMMARY
OBS-R3Q-C01 is a host-side emitter defect, not a client-side resolver defect, and the whole chain is non-comment identical between b150 (ba6d8c39) and new upstream main (3af5ddae) — `git diff -w` over the six chain files shows only comment/include-comment rewording. The chain: on a host placement the game destroys the in-hand display husk; that husk was deliberately never expressed (host_spawn_watcher.cpp:370 excludes the hand actor from adoption), so it carries no Element row; prop_destroy_seam.cpp:45/:131 therefore stamps `elementId = 0` (the protocol's "sender had no Element" sentinel, protocol.h:1090) while still stamping the box's logical key, and :149 broadcasts it. The receiver's range gate exempts zero (event_dispatch_entity.cpp:236), so the packet is admitted; remote_prop_destroy.cpp:133-135 skips eid resolution because eid is 0, falls to :150 `ResolveLiveActorByKey`, gets an O(1) index hit on the mirror bound one line earlier at eid 5975, and :190 destroys it. The guard asymmetry is exact: the SPAWN side of the host excludes hand-axis actors in three places (host_spawn_watcher.cpp:370, prop_drop_intent.cpp:140 and :281) and the client-place direction additionally defers its intent by one tick specifically so the husk's same-key DESTROY lands before the spawn (prop_drop_intent.h:12-15 names this exact hazard) — the host-authored direction has no counterpart, and the DESTROY seam contains no hand-axis test at all. The minimal fix is at the emitter, in `DestroySeamBody`, scoped to the host role: for a keyed destroy whose eid is 0, do not broadcast if another live local actor still holds that key. It cannot regress the legitimate hand-actor destroy because that one carries a nonzero eid (measured: host `eid=5974`, client resolved it by eid onto the correct actor) and never enters the gate. 46b77b92 is orthogonal — it is the SPAWN lane, and the C01 destroy was never range-gated — but it is the reason the fix must not be written as a blanket keyed-zero-eid destroy refusal. New upstream main added `unresolved_pose_ledger` (remote_prop.cpp:158-168), which reports C01's aftermath as a SUSTAINED unresolved pose stream but does not fix it.
